Week 2, Open Weights. Synthetic data for the use case.

Summary

A GRC consultant needs about four days per client to decide which maturity level the client's evidence supports for each control. The team cannot keep up with the organisations that must self-assess by law. This week I generated synthetic requests for three controls, varied along four axes, so I can test a system for this task before any real client data is allowed near it.

The result is 548 rows, a datasheet that says what they can and cannot show, the code that made them, and a review of 20 rows with the project lead. The rows are not in the repo, only the code and the datasheet.

Update, 20 Oct. I relabelled all 548 rows with Opus 5.5: same documents, new levels. It agrees with the project lead on all six rejected levels (the prompt's rules came from that review, so this is not an independent test), changed 463 of 1,096 levels, and found 313 rows whose documents do not match their recipe. Details at the end of the datasheet. The video shows the first version.

The axes

One request is one control plus the client's evidence documents. Each axis has a reason.

AxisValuesWhy
control3 controls: top-level cybersecurity policy, roles and duties, staff awareness trainingThe system must work on every topic, and the implementation scale is different for each control.
document_stateadopted and in force, draft, not adopted or not signed, incomplete, badly or vaguely worded, outdatedGood content does not make a document valid. Adopted, up to date and complete are separate things.
document_relationdocuments agree, contradict each other, several versions, a later event changes the situation, refers to a document that was not submittedThe system has to know which document is authoritative and notice what is missing.
implementation_evidencefull, partial near a level threshold, paper only, evidence only, irrelevant documents only (decline)Implementation must not be inferred from paper. Without relevant evidence there is no level.

3 × 6 × 5 × 5 is 450 combinations. I removed the ones that cannot exist, which leaves 288. For example, with irrelevant documents only, the document axes do not apply.

The script generate.py builds every possible combination, asks the model for rows for each one, removes near-duplicates and keeps only rows that fit the schema.

The final dataset has 548 rows: 555 schema-valid, 1 removed after reading, 6 removed after the project lead's review.

255 lines needed one extra closing brace removed before they could be read. 33 lines could not be read at all.

The rerun of the 13 dead combinations is not in generate.py. On 2026-10-24 I checked all 548 rows together: dedupe at 0.7 still drops nothing, and the leak check gives the same 16 hits.

Settings: openai/claude-haiku-4-5 through the internal gateway, temperature 0.7 (0.3 for the decline combinations), top_p 0.9, 2 rows per call, dedupe threshold 0.7, 288 combinations.

The threshold is 0.7 because each row is a whole package of documents, and even the closest pair is only 0.49 alike. At 0.4 I would throw away real test cases. At 0.7 nothing was dropped.

What I removed

After reading (1 row). A POL-001 row, draft later adopted, full evidence. Implementation level 5 is too generous. The documents only say implementation has started, and level 5 also needs updates and a yearly effectiveness review.

After the project lead's review (6 rows). The level is not backed by the documents, so the label is wrong. I kept none of them, even though the scenarios are realistic.

The leak check read 50 rows spread across all controls and all evidence values, with an automated pre-screen for e-mails, URLs, personal ID numbers, IBANs, phone numbers, company names and code-like references. Apart from invented company names (for example "TechCorp"), nothing of that kind was found. Person names in the rows are invented, and I checked them against people I know.

What the data cannot validate

It is prototyping data. It can show that the script runs, that the output keeps to the schema, that every axis combination has rows, and, for the 235 rows that match their recipe, where the system breaks by axis. It cannot support a production accuracy number.

  • Other controls. The rows cover 3 controls out of a catalog of more than a hundred. The implementation scale is different for each, so results here say nothing about the rest.
  • The levels themselves. The generator labelled every row and nobody confirmed the labels. Of the 50 rows I read, one level was too generous. Others like it are likely still in.
  • Real document formats. Every document is clean text. Real packages have scans, Word files with tracked changes and long e-mail chains.
  • Real package size. Real clients send more and longer documents, so the sentence that decides the level is harder to find.
  • Technical evidence and evidence sent later. Not in the data. This came from the project lead's review.
  • How often each situation happens. The percentages in this data are not like those at real clients: every combination got 2 rows, so each document state is about 16% of the rows.

These rows must never be compared against the consultants' final levels from past client analyses, or against the reference assessment the golden levels came from. They must never be reported as those results or mixed with them in one score.

One more limit: goldens 3, 5 and 6 were shown to the generator as format examples. If Week 8 tunes on this file, scores on those three goldens are not independent. By the dedupe measure, 0 rows overlap with the goldens at threshold 0.7. The closest pair is 0.33.

Review with the project lead

I went through 20 rows and the datasheet together. Three notes.

  • Never happens: nothing impossible, but six levels are not backed by the documents (examples 4, 5, 6, 8, 9 and 18 of the 20).
  • Missing: scans, big packages, technical evidence like config exports and logs, evidence sent later.
  • Worry if public: that the data looks validated when nobody checked the levels.

I removed the six rows. A consultant should check a sample of levels before Week 4.

Bring it to work

The maturity assessment tool cannot be tested on real client evidence until each client consents to having their documents processed with AI. The secure infrastructure on our side is already in place.

  • Data: generate from a description (the catalog, the level criteria and rules such as "board minutes outrank the intranet"), never from client records. Use past analyses only to check that the generated cases look like real ones.
  • Model: the internal AI gateway in our GCP landing zone, under an enterprise agreement, so the data stays inside our environment. The gateway offers several hosted models, so the model can change without the data leaving.
  • Approval: a deployment review with DevOps, then security and privacy reviews with the teams that own them, before anything goes to production. The product owner asks clients for consent to have their documents processed with AI and encourages them to join.
